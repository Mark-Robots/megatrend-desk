Il tool si aspetta un JSON con rendimenti mensili per settore, universo point-in-time (con date di ingresso/uscita) e le selezioni effettive del sistema a ogni ribilanciamento:

{
  "meta":   { "name": "Sector Rotation v3 — RRG+Weinstein" },
  "months": ["2016-01", "2016-02", "..."],
  "sectors": [
    { "id": "XLK", "name": "Technology", "from": "2016-01", "to": "2025-12" },
    { "id": "XLC", "name": "Comm. Services", "from": "2018-07", "to": "2025-12" }
  ],
  "returns": { "XLK": [0.012, -0.031, "..."], "XLC": [null, null, "..."] },
  "rebalances": [
    { "month": "2016-01", "selected": ["XLK","XLV","XLP"] },
    { "month": "2016-04", "selected": ["XLK","XLE","XLI"] }
  ]
}

returns[id] è allineato a months; usa null dove il settore non esiste. I mesi di rebalances devono comparire in months.

Cosa testa (e cosa no)
  • Testa: se la selezione dei settori aggiunge segnale rispetto al caso, a parità di calendario, numero di posizioni e universo point-in-time. Le scimmie pescano solo tra i settori esistenti a quella data: niente survivorship bias.
  • Metrica: percentile empirico del CAGR del sistema nella distribuzione dei CAGR casuali. Equivale a un p-value: percentile 97° → p ≈ 0,03.
  • Assunzioni: pesi uguali, ribilanciamento mensile interno alla selezione, nessun costo di transazione (uguale per sistema e scimmie, quindi neutrale al confronto), esecuzione a fine mese.
  • Non testa: il timing di ingresso/uscita intra-mese, i time-stop (TS3/TS6), la scelta del numero di posizioni, la robustezza out-of-sample. Un percentile alto qui è condizione necessaria, non sufficiente.
  • Lettura onesta: sotto l'80° percentile la selezione è indistinguibile dal caso. Tra 80° e 94° il segnale è debole: potrebbe non sopravvivere ai costi. Dal 95° in su c'è evidenza di skill nella selezione.
